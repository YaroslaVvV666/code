# Масштабирование: много воркеров + nginx

Сервер — один процесс Python, и из-за общего замка и GIL он нагружает **одно ядро**. Чтобы задействовать
все ядра машины, запускается **несколько процессов-воркеров** за балансировщиком nginx. Это первый и самый
дешёвый шаг к нагрузке на миллион пользователей — умножает пропускную способность примерно на число ядер.

## Как запустить несколько воркеров

```bash
export DATABASE_URL="postgres://orbita:ПАРОЛЬ@127.0.0.1:5432/orbita"   # для продакшена — PostgreSQL
export REDIS_URL="redis://127.0.0.1:6379/0"                           # общее realtime-состояние (звонки/набор/QR)
export ORBITA_WORKERS=8        # сколько процессов (обычно = числу ядер)
python3 Server/server.py
```

**REDIS_URL обязателен при нескольких воркерах.** Звонки, индикатор набора и вход по QR связывают *разных*
пользователей/устройства, которых sticky-сессии разводят по разным воркерам, поэтому это короткоживущее
состояние должно быть общим. С одним воркером Redis не нужен (состояние живёт в памяти, как раньше). Поставить
Redis: `sudo apt install redis-server`.

Мастер-процесс поднимет воркеры на портах `PORT, PORT+1, … PORT+N-1` (по умолчанию `8080..8087`),
будет следить за ними и перезапускать упавшие. Сам мастер запросы не обслуживает — перед воркерами
ставится nginx.

- **Один воркер (по умолчанию, `ORBITA_WORKERS` не задан)** — как раньше: один процесс на `PORT`, nginx не
  обязателен. Для разработки и небольшой нагрузки ничего менять не нужно.
- **PostgreSQL обязателен для многих воркеров.** На SQLite несколько процессов делят один файл — под
  нагрузкой будут блокировки. См. `docs/postgresql.md`.

## nginx: «липкие» сессии (обязательно)

Часть состояния (кэш лент, вход по SMS-коду, 2FA, мастер-бот стикеров) живёт **в памяти воркера**.
Поэтому один и тот же пользователь должен всегда попадать в один и тот же воркер — это и есть «липкая»
(sticky) сессия. nginx направляет по токену авторизации, а до входа — по IP.

`/etc/nginx/sites-available/orbita`:

```nginx
# ключ липкости: у вошедших — токен, у остальных (ping, вход по коду) — IP
map $http_authorization $orbita_sticky {
    default   $binary_remote_addr;
    "~.+"     $http_authorization;
}

upstream orbita_workers {
    hash $orbita_sticky consistent;   # один пользователь — всегда один воркер
    server 127.0.0.1:8080;
    server 127.0.0.1:8081;
    server 127.0.0.1:8082;
    server 127.0.0.1:8083;
    server 127.0.0.1:8084;
    server 127.0.0.1:8085;
    server 127.0.0.1:8086;
    server 127.0.0.1:8087;
    keepalive 128;
}

server {
    listen 443 ssl http2;
    server_name ваш-домен;

    ssl_certificate     /etc/letsencrypt/live/ваш-домен/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/ваш-домен/privkey.pem;

    client_max_body_size 25m;          # загрузка медиа

    location / {
        proxy_pass http://orbita_workers;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_read_timeout 120s;       # длинные опросы (звонки) не рвём раньше времени
    }
}
```

Число `server 127.0.0.1:808x` в upstream должно совпадать с `ORBITA_WORKERS`.

> **Клиенту сообщайте адрес сервера как `https://ваш-домен` (nginx), а не порт воркера.** В приложении это
> тот же адрес сервера, что и раньше.

## Что уже работает на нескольких воркерах

- Все данные (профили, сообщения, группы, лента, статистика) — в общей БД, поэтому видны всем воркерам.
- Гонка «два запроса создают одно и то же»: её ловит уникальное ограничение БД, дубликат получает честный
  `409 conflict`, а не ошибку сервера. Проверено: 40 одновременных попыток создать один аккаунт на 3 воркерах
  → ровно 1 успех, 39 отказов, ноль сбоев.
- Отложенные сообщения и протухшие истории обрабатывает ровно один воркер (№0) — без двойной доставки.
- **Звонки, индикатор набора и вход по QR** работают на любом числе воркеров через общий Redis (шаг 1b). Проверено:
  звонок, где абонент и вызываемый обслуживаются *разными* воркерами, полностью проходит (входящий → offer →
  answer → ICE → завершение), «занят» определяется между воркерами, печатающий сосед и approve QR тоже видны.

## Про Redis (шаг 1b)

Короткоживущее realtime-состояние (объект звонка, очередь сигналов offer/answer/ICE, «кто с кем в звонке»,
индикатор набора, заявки на вход по QR) хранится в `Server/sharedstate.py` с двумя бэкендами:

- **память** — по умолчанию (один воркер), поведение как раньше;
- **Redis** — если задан `REDIS_URL`; тогда состояние общее для всех воркеров и процессов/машин.

Это не основная база: данные тут временные, на диск не пишутся и легко восстанавливаются (в худшем случае —
переустановить активный звонок). Redis держит их в памяти и раздаёт всем воркерам мгновенно.

## Кэш (шаг 2): меньше нагрузки на базу

Самый частый запрос к базе — проверка токена на КАЖДЫЙ запрос (JOIN `sessions`+`users`). Плюс частые опросы
списка чатов и лент. Всё это кэшируется в `SHARED` (память при одном воркере, Redis — при нескольких, общий кэш):

- **Проверка токена** кэшируется на `ORBITA_AUTH_CACHE_TTL` секунд (по умолчанию 15; `0` — выключить). Пока
  пользователь только читает (опрашивает), база для авторизации не дёргается вовсе.
- **Списки чатов и ленты** (`/v1/chats`, `/v1/posts`, `/v1/reels`) кэшируются на 1.5–8 секунд.

Инвалидация точная и безопасная: у каждого пользователя есть счётчик версии (`uver`), который растёт при любом
его действии (сообщение, правка профиля, выход, отключение устройства). Кэш авторизации и кэш лент привязаны к
этому счётчику, поэтому:

- правка профиля видна сразу (а не через TTL), в том числе на других воркерах;
- **выход и отключение чужого устройства действуют мгновенно на всех воркерах** — отозванный токен перестаёт
  работать на следующем же запросе, устаревшего «окна» нет.

Проверено на 3 воркерах + Postgres + Redis: смена имени видна на другом воркере сразу; убитая сессия
отклоняется (401) на всех воркерах немедленно; обычные функции без регрессий; режим одного воркера (без Redis)
ведёт себя так же.

## Push вместо опроса (шаг 3)

Раньше клиент постоянно дёргал сервер: список звонков каждые ~250 мс, чаты и ленту — периодически. На сотнях
тысяч онлайн это главный источник нагрузки (поток пустых запросов). Теперь есть **long-poll**:

- `GET /v1/events/wait?timeout=25` — запрос **висит** на сервере, пока для пользователя не появится событие
  (или не выйдет таймаут), и возвращает список тем: `dm`, `group`, `call`, `typing`. Клиент по ним обновляет
  только нужное и снова встаёт на ожидание. Вместо десятков пустых опросов в секунду — один висящий запрос.
- Событие публикуется там, где оно рождается: новое личное сообщение, сообщение в группе, сигнал звонка
  (входящий/ответ/ICE/завершение), начало набора. Через Redis-pub/sub побудка доходит до того воркера, где
  висит клиент, поэтому работает на любом числе воркеров и машин.
- **Полная совместимость:** старые эндпоинты опроса (`/v1/calls/poll`, `/v1/chats`, …) работают как прежде —
  приложение может переходить на long-poll постепенно.

Проверено на 3 воркерах + Postgres + Redis: висящий `events/wait` будится входящим сообщением и звонком с
**другого воркера** за ~20 мс; таймаут возвращает пусто; старый опрос и остальные функции без регрессий; режим
одного воркера (без Redis) ведёт себя так же.

Внутри воркера каждый висящий long-poll занимает поток (со сниженным стеком). Это держит десятки тысяч ожидающих
на воркер; дальше масштабируют числом воркеров и машин. Переход на полностью асинхронную модель (на сотни тысяч
соединений в одном процессе) — возможный следующий шаг, уже отдельный.

## Медиа в объектном хранилище (шаг 4)

Фото, видео и голосовые раньше лежали на диске сервера — это упирается в размер диска одной машины и не
делится между воркерами. Теперь хранилище выбирается переменной окружения, код один и тот же
(`Server/blobstore.py`):

- **Диск** (по умолчанию) — как было, `~/.orbita/data/media-v2`. Ничего настраивать не нужно.
- **Объектное хранилище S3** — при `ORBITA_S3_BUCKET`. Подходит AWS S3, MinIO, Yandex Object Storage и любое
  S3-совместимое. Объём не ограничен диском, файлы доступны всем воркерам и переживают пересоздание контейнера.

```bash
export ORBITA_S3_BUCKET=orbita-media
export AWS_ACCESS_KEY_ID=...            # ключи доступа к хранилищу
export AWS_SECRET_ACCESS_KEY=...
# для не-AWS (MinIO/Yandex): endpoint и регион
export ORBITA_S3_ENDPOINT=https://storage.yandexcloud.net
export ORBITA_S3_REGION=ru-central1
```

Важно про приватность: файлы **хранятся зашифрованными** (ключом сервера), сервер остаётся точкой расшифровки
и отдачи. Поэтому это приватное хранилище, а не публичная раздача. CDN перед `/media` имеет смысл для публичных
ассетов (ответы уже помечены `Cache-Control: immutable`); приватные чаты через CDN не раздаются, чтобы кэш не
держал расшифрованное.

Как это устроено: при загрузке файл шифруется во временный файл, проходит проверку и заливается в бакет; при
отдаче видео `_S3Reader` берёт только нужные байтовые диапазоны (Range), поэтому перемотка видео не тянет весь
файл. Пересылка/копирование по-прежнему перешифровывает под нового владельца.

Проверено: загрузка → скачивание байт-в-байт и запрос диапазона (и на диске, и в S3 через мок); полная и
серединная расшифровка видео из S3 совпадают с оригиналом; удаление очищает и бакет.

## Ограничение частоты / защита от злоупотреблений (шаг 5)

Публичный сервер нужно защищать от спама и случайного «залипшего» клиента, который бьёт в одну ручку тысячи
раз. Разделение труда:

- **Грубый лимит по IP — в nginx** (он видит IP раньше всех и дешевле всего отбивает потоп):

  ```nginx
  limit_req_zone $binary_remote_addr zone=orbita:10m rate=20r/s;
  server {
      location / {
          limit_req zone=orbita burst=40 nodelay;
          proxy_pass http://orbita_workers;
          # ... (как выше)
      }
  }
  ```

- **Осмысленные лимиты по пользователю и действию — в сервере** (nginx не знает, кто это). Общие для всех
  воркеров (через Redis), поэтому их нельзя обойти, раскидывая запросы по разным воркерам. По умолчанию
  включены (`ORBITA_RATELIMIT=0` — выключить):

  | Действие | Лимит |
  |---|---|
  | Создание аккаунта (на IP) | 30 / час |
  | Отправка сообщений (на пользователя) | 300 / минуту |
  | Загрузка файлов | 120 / минуту |
  | Создание групп/каналов | 30 / час |
  | Исходящие звонки | 30 / минуту |

  При превышении — ответ `429` с полем `retry_after` (через сколько секунд повторить). Лимиты подобраны выше
  любой нормальной активности — обычного пользователя они не задевают.

Проверено: обычная переписка проходит; на 301-м сообщении в минуту приходит `429`; создание аккаунтов режется
на 31-м; лимит общий для воркеров (запросы на разные воркеры считаются вместе).

## Сколько это даёт

На машине с N ядрами — примерно ×N к пропускной способности относительно одного процесса. Дальше масштабируют
не только воркерами на одной машине, но и несколькими машинами за одним nginx (адреса воркеров в upstream
указывают на разные хосты), плюс Redis-кэш (шаг 2) и уход от постоянного опроса (шаг 3).
