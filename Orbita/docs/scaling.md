# Масштабирование: много воркеров + nginx

Сервер — один процесс Python, и из-за общего замка и GIL он нагружает **одно ядро**. Чтобы задействовать
все ядра машины, запускается **несколько процессов-воркеров** за балансировщиком nginx. Это первый и самый
дешёвый шаг к нагрузке на миллион пользователей — умножает пропускную способность примерно на число ядер.

## Как запустить несколько воркеров

```bash
export DATABASE_URL="postgres://orbita:ПАРОЛЬ@127.0.0.1:5432/orbita"   # для продакшена — PostgreSQL
export ORBITA_WORKERS=8        # сколько процессов (обычно = числу ядер)
python3 Server/server.py
```

Мастер-процесс поднимет воркеры на портах `PORT, PORT+1, … PORT+N-1` (по умолчанию `8080..8087`),
будет следить за ними и перезапускать упавшие. Сам мастер запросы не обслуживает — перед воркерами
ставится nginx.

- **Один воркер (по умолчанию, `ORBITA_WORKERS` не задан)** — как раньше: один процесс на `PORT`, nginx не
  обязателен. Для разработки и небольшой нагрузки ничего менять не нужно.
- **PostgreSQL обязателен для многих воркеров.** На SQLite несколько процессов делят один файл — под
  нагрузкой будут блокировки. См. `docs/postgresql.md`.

## nginx: «липкие» сессии (обязательно)

Часть состояния (кэш лент, вход по SMS-коду, 2FA, мастер-бот стикеров) живёт **в памяти воркера**.
Поэтому один и тот же пользователь должен всегда попадать в один и тот же воркер — это и есть «липкая»
(sticky) сессия. nginx направляет по токену авторизации, а до входа — по IP.

`/etc/nginx/sites-available/orbita`:

```nginx
# ключ липкости: у вошедших — токен, у остальных (ping, вход по коду) — IP
map $http_authorization $orbita_sticky {
    default   $binary_remote_addr;
    "~.+"     $http_authorization;
}

upstream orbita_workers {
    hash $orbita_sticky consistent;   # один пользователь — всегда один воркер
    server 127.0.0.1:8080;
    server 127.0.0.1:8081;
    server 127.0.0.1:8082;
    server 127.0.0.1:8083;
    server 127.0.0.1:8084;
    server 127.0.0.1:8085;
    server 127.0.0.1:8086;
    server 127.0.0.1:8087;
    keepalive 128;
}

server {
    listen 443 ssl http2;
    server_name ваш-домен;

    ssl_certificate     /etc/letsencrypt/live/ваш-домен/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/ваш-домен/privkey.pem;

    client_max_body_size 25m;          # загрузка медиа

    location / {
        proxy_pass http://orbita_workers;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_read_timeout 120s;       # длинные опросы (звонки) не рвём раньше времени
    }
}
```

Число `server 127.0.0.1:808x` в upstream должно совпадать с `ORBITA_WORKERS`.

> **Клиенту сообщайте адрес сервера как `https://ваш-домен` (nginx), а не порт воркера.** В приложении это
> тот же адрес сервера, что и раньше.

## Что уже работает на нескольких воркерах

- Все данные (профили, сообщения, группы, лента, статистика) — в общей БД, поэтому видны всем воркерам.
- Гонка «два запроса создают одно и то же»: её ловит уникальное ограничение БД, дубликат получает честный
  `409 conflict`, а не ошибку сервера. Проверено: 40 одновременных попыток создать один аккаунт на 3 воркерах
  → ровно 1 успех, 39 отказов, ноль сбоев.
- Отложенные сообщения и протухшие истории обрабатывает ровно один воркер (№0) — без двойной доставки.

## Что требует следующего шага (1b, общее хранилище Redis)

Пока держат состояние в памяти воркера и работают **в пределах одного воркера**:

- **Звонки** — сигналинг (offer/answer/ICE) связывает *двух разных* пользователей, которые sticky-сессии
  разводят по разным воркерам. До шага 1b звонок между абонентами гарантирован только внутри одного воркера.
- **Индикатор набора** («печатает…») — тоже между разными пользователями.
- **Вход по QR-коду** — связывает телефон и десктоп (разные устройства → разные воркеры).

На шаге 1b это эфемерное состояние выносится в Redis, после чего ограничение снимается и всё работает на
любом числе воркеров.

## Сколько это даёт

На машине с N ядрами — примерно ×N к пропускной способности относительно одного процесса. Дальше масштабируют
не только воркерами на одной машине, но и несколькими машинами за одним nginx (адреса воркеров в upstream
указывают на разные хосты), плюс Redis-кэш (шаг 2) и уход от постоянного опроса (шаг 3).
